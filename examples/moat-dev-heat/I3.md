# Standalone heating host (draft)

Goal (2026-09-28): the heating system runs on `pi-i3` (`i3.pi.s`) on its
own FlashMQ broker and MoaT-Link server, so that it keeps working when the
rest of the network is down. A MoaT-Link-to-Link gateway on `s-bed`
copies what crosses the boundary between the two Link instances.

## On i3

- FlashMQ, MoaT-Link server (its own server name, e.g. `i3`).
- The Link pollers (`moat modbus dev poll`, see README.md) for the serial
  and Modbus-TCP devices attached to i3.
- The heat units (`target`, `heat_valve`, `flow`, `pump`, `pellet`,
  `selector`, `errors`, `frost`, `watchdog`), the `pwm` daemon and the
  Solvis monitor.
- The heat configuration (`cfg.app.heat.*`) and state (`app.heat.*.state`)
  live here.

Everything runs from systemd units: `flashmq`, `moat-link-server`,
`moat-modbus-poll@FILE` (package `moat-modbus`), `moat-heat.service` or
`moat-heat@UNIT` (package `moat-dev-heat-service`), `moat-heat-pwm`,
`moat-heat-modbus-mon`.

The watchdog (`moat-heat@watchdog`) should not run in the same process as
the pump unit. On another host it would have to see the pump's service
announcement, which lives under `run.*`, and the Link gateway doesn't
sync that: to be decided (see Open questions).

## Gateways on s-bed

One `link` gate per subtree; each gate syncs its subtree in both
directions, at the same path on both servers (`run.*` is never synced).
The gate's `backend` points at i3's broker, `server` names i3's Link
server.

| Subtree | Direction of the data | Why |
| --- | --- | --- |
| `heat` | i3 → main | sensors and commands, for Home Assistant (`gate.hass.heat`) and monitoring |
| `app.heat` | both | unit outputs (monitoring), overrides (operators, HA bridge) |
| `cfg.app.heat` | both | edit the configuration from anywhere; i3 keeps working with the last copy |
| `schema.app.heat` | i3 → main | override schemas, so writes on main are checked too |
| `grid.s` (the meters polled on i3) | i3 → main | power readings |
| `home.ass.dyn.switch.heizung` | both | HA switches in (`.cmd`), feedback out (`.state`) |
| `home.ass.dyn.binary_sensor.heizung` | i3 → main | pump, de-ice feedback |
| `home.ass.dyn.sensor.heizung` | i3 → main | COP |
| `home.ass.dyn.switch.plug-n5` | both | the heat-pump loop valve (frost unit): `.cmd` out, `.state` in |
| `home.ass.dyn.sensor.temp.garten_kompost_schatten` | main → i3 | outside temperature (selector) |
| `home.ass.state.input_boolean.test_override_on`, `home.ass.state.input_number.test_override_pct` | main → i3 | PWM test override (`pwm` daemon) |
| `temp.avg.temp.aussen_kompost` | main → i3 | outside temperature for the heating curve (target) |
| `temp.min.forecast` | main → i3 | forecast minimum (selector); or run the forecast job on i3 |

If the network is down, i3 keeps the last values of the inputs from
main: the selector latches, the target unit holds the outside
temperature for `freeze`, then heats to the curve's day/night value.

## Open questions

- Which poller files run on i3? (`heat` and `stiebel`/`stiebelfake`
  certainly; `aux` polls meters on "the other host".)
- Where are `temp.avg.temp.aussen_kompost.min` and the forecast produced?
  If on main, they go through the gateway as above.
- The name of i3's MoaT-Link server, and how the gateway reaches i3's
  broker (the `backend` override).
- Where the watchdog runs: a separate `moat-heat@watchdog` process on i3
  covers a crashed or killed pump unit, but not a dead i3.
