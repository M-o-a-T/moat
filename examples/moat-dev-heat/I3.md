# Standalone heating host

Goal (2026-09-28): the heating system runs on `pi-i3` (`i3.pi.s`) on its
own FlashMQ broker and MoaT-Link server (server name `pi-i3`), so that it
keeps working when the rest of the network is down. A MoaT-Link-to-Link
gateway on `s-bed` copies what crosses the boundary between the two Link
instances. i3 knows nothing about Home Assistant.

## On i3

- FlashMQ, MoaT-Link server (server name `pi-i3`).
- The Link pollers (`moat modbus dev poll`, see README.md): `heat`,
  `stiebel`, `stiebelfake`. (`aux` moves to s-bed.) The Modbus-TCP hosts
  of `modbus.heat.yaml` (`wp.hz.smurf.noris.de`,
  `pellet.hz.smurf.noris.de`) go into `/etc/hosts`, so that no DNS is
  needed.
- Local clients reach FlashMQ and the Link server through Unix sockets,
  so they keep working if networking is dead: FlashMQ gets a
  `listen { inet_protocol unix … }` block, the Link server a Unix-socket
  listener, and `/etc/moat/moat.yaml` uses `backend.transport: unix` and
  `client.path` (with `client.local_only`).
- The heat units (`target`, `heat_valve`, `flow`, `pump`, `pellet`,
  `selector`, `errors`, `frost`, `watchdog`), the `pwm` daemon and the
  Solvis monitor.
- The heat configuration (`cfg.app.heat.*`) and state (`app.heat.*.state`)
  live here.

Everything runs from systemd units: `flashmq`, `moat-link-server`,
`moat-modbus-poll@FILE` (package `moat-modbus`), `moat-heat.service` or
`moat-heat@UNIT` (package `moat-dev-heat-service`), `moat-heat-pwm`,
`moat-heat-modbus-mon`.

The watchdog (`moat-heat@watchdog`) runs on i3, in its own process: it
covers a crashed or killed pump unit. A dead or unreachable i3 shows up
on the main side as a dead gateway (fast detection: moat-p4c1).

## Gateways on s-bed

One `link` gate per subtree; each gate syncs its subtree in both
directions, at the same path on both servers.

The gate's `backend` points at i3's broker, `server` names i3's Link
server.

| Subtree | Direction of the data | Why |
| --- | --- | --- |
| `heat` | i3 → main | sensors and commands, for Home Assistant (`gate.hass.heat`) and monitoring |
| `app.heat` | both | unit outputs (monitoring), overrides (operators, HA bridge) |
| `cfg.app.heat` | both | edit the configuration from anywhere; i3 keeps working with the last copy |
| `schema.app.heat` | i3 → main | override schemas, so writes on main are checked too |
| `grid.s.heat` (the meters polled on i3) | i3 → main | power readings |
| `temp.avg.temp.aussen_kompost` | main → i3 | outside temperature for the heating curve (target) |
| `temp.min.forecast` | main → i3 | forecast minimum (selector); the forecast job runs elsewhere |

No `home.ass.*` path crosses the gateway: Home Assistant entities are
the main node's business. MoaT-Link job scriptlets on s-bed (or another
runner) copy them between `home.ass.dyn` and `heat` / `app.heat` in
whichever direction is needed (`transform.copy.value`; needs
moat-zshv.12 on main), and the heat units use those paths.

The entities, copy jobs and override jobs are in HA.md.

## Configuration

### i3

FlashMQ gets a second listener (check the option names against the
installed version's `flashmq.conf(5)`):

```
listen {
    protocol mqtt
    inet_protocol unix
    unix_socket_path /run/flashmq/mqtt.sock
}
```

`/etc/moat/moat.yaml`, the parts that differ from the main node:

```yaml
link:
  backend:
    driver: mqtt
    codec: std-cbor
    transport: unix
    path: /run/flashmq/mqtt.sock
  client:
    path: /run/moat/link/socket
    local_only: true
  server:
    ports:
      local:
        port: /run/moat/link/socket
      main:
        host: 0.0.0.0
        port: 27587
```

The TCP listeners of both the broker and the Link server stay: the
gateway on s-bed connects through them. Start the server as
`moat-link-server@pi-i3`.

### s-bed

The gates live below `gate.i3`, so one service runs them all:

```shell
G="-d link -v server pi-i3 -v backend.host i3.pi.s"
moat link gate i3.heat set $G -S heat
moat link gate i3.app set $G -S app.heat
moat link gate i3.cfg set $G -S cfg.app.heat
moat link gate i3.schema set $G -S schema.app.heat
moat link gate i3.grid set $G -S grid.s
moat link gate i3.t_out set $G -S temp.avg.temp.aussen_kompost
moat link gate i3.t_min set $G -S temp.min.forecast
systemctl enable --now moat-link-gate@i3
```

Don't start the gates on a host whose `link.client.path` is set until
moat-schn is fixed: the gate would talk to the local server instead of
i3's.

## Deployment order

1. i3: install FlashMQ and the `moat-link-server`, `moat-modbus` and
   `moat-dev-heat-service` packages; configure as above; start the
   broker and the Link server. The server starts empty.
2. s-bed: create and start the `cfg`, `schema`, `app`, `t_out` and
   `t_min` gates. Check on i3 that `cfg.app.heat` and both temperature
   inputs have arrived (`moat link -m data temp.min.forecast get -r`).
3. Move the pollers (README.md): on s-bed stop the MoaT-KV pollers for
   `heat`, `stiebel` and `stiebelfake`; on i3
   `systemctl enable --now moat-modbus-poll@heat` etc. `aux` switches
   to the Link poller on s-bed.
   From here until step 5 nothing controls the heating: keep the gap
   short.
4. s-bed: create the `heat` and `grid` gates. The values polled on i3
   show up on main again.
5. i3: start `moat-heat-pwm`, `moat-heat-modbus-mon`,
   `moat-heat@watchdog` and `moat-heat` (the cutover proper,
   moat-n84.24; the legacy controller must be stopped first).

## When the network is down

i3 keeps the last values of the inputs from
main: the selector latches, the target unit holds the outside
temperature for `freeze`, then heats to the curve's day/night value.
